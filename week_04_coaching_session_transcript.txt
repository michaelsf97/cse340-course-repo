That `req.flash('success', 'Category created successfully.')` right before `res.redirect(...)` shows how a flash message gets stored across the redirect so the next page can read it once—and if an exception happens in the `try` block, `next(error)` hands it off to your error middleware.

Why do we need a session store behind flash messages when doing a redirect (`res.redirect(...)`), instead of just passing a normal variable into `res.render(...)`?

--- Michael ---
Because of a session store allows us to save those flash messages and sent back to then likely acquire a POST inside a form

--- Coach ---
Right—because HTTP is stateless and a redirect triggers a brand-new request, the session store holds that flash message temporarily between requests so it's there when the browser loads the next page instead of getting lost.

--- Coach ---
That `validateCategory` chain is super clean—`.trim()` strips leading/trailing spaces, `.notEmpty()` catches empty values, and `.isLength({ min: 3, max: 100 })` enforces the character range. (One small detail to keep in mind: `.trim()` removes spaces at the start and end of the string rather than spaces between words like "Community Health", and `validationResult(req)` passes those errors into `errors.array()` for the EJS template.)

Why is running checks like `validateCategory` on the server still essential when your HTML form already has attributes like `required` or `maxlength`?

--- Michael ---
Because of a user can open DevTools and remove then but after that server-side validation is available to deter this process. And, to protect data from website and avoid attacks XXS attacks

--- Coach ---
Spot on—anyone can inspect the page in DevTools, delete `required` or `maxlength` attributes, or send raw requests directly to the endpoint, so server-side validation is your real gatekeeper before data reaches the database (and pairing validation with output escaping in EJS helps protect against XSS).
